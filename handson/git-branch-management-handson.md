## ブランチを「下書き用コピー」で理解する

ブランチとは、**本体（main）を壊さずに安全に作業するための「下書き空間」** です。

| 日常の例 | Git |
|----------|-----|
| 本番の資料はそのままに、コピーで編集 | ブランチを切って作業する |
| 上司に確認してもらう | プルリクエストでレビューを依頼する |
| 「OK」が出たら本番に反映 | mainにマージする |
| 同僚と同じ箇所を別々に直した | コンフリクト（後述） |

---

## ステップ 1：コミットと履歴を確認する

まず「変更の記録がどう積み重なるか」を体感しましょう。

```bash
# 現在の変更履歴を見る
git log --oneline
```

**見るべきポイント：**

- 左端の短い文字列（例：`a3f9c1b`）＝ コミットID（セーブポイントの番号）
- その右側＝ コミットメッセージ（何をしたかのメモ）
- 上にあるほど新しい

**確認問題：** 今見ている履歴のうち、一番最新のコミットは何をした変更ですか？

---

## ステップ 2：mainブランチを「幹」として理解する

```bash
# 今自分がどのブランチにいるか確認する
git branch
```

`main` の前に `*` がついていれば、mainブランチにいます。

**mainブランチのルール（多くのチームで共通）：**

- mainは常に「動く状態」を保つ
- 直接mainで作業しない
- レビューを経た変更だけがmainに入る

---

## ステップ 3：ブランチを作って移動する

```bash
# 新しいブランチを作り、そこへ移動する
git checkout -b feature/自分の名前-練習

# 例：
git checkout -b feature/tanaka-practice
```

**確認：** ブランチが切り替わったか確認しましょう。

```bash
git branch
```

`*` が新しいブランチ名の前に移っていればOKです。

> **ポイント：** この時点で `main` はまったく変わっていません。
> 2つの「現実」が並行して存在している状態です。

---

## ステップ 4：ブランチ上で変更を加えてコミットする

```bash
# 練習用ファイルを編集する（内容は何でもOK）
# → エディタでファイルを開いて何か書いて保存

# 変更を確認する
git diff

# ステージングに追加する
git add ファイル名

# コミットする
git commit -m "練習：〇〇を追加"
```

**確認：** `git log --oneline` を実行して、自分のコミットが追加されているか確認しましょう。

```bash
# mainに切り替えて、mainには変更が入っていないことを確認する
git checkout main
git log --oneline
```

mainには自分のコミットが**ない**はずです。これがブランチの意味です。

## ステップ 5：プルリクエストを出す

GitHubのUI操作です。

1. GitHubのリポジトリページを開く
2. 「Compare & pull request」ボタンをクリック（自動で表示されることが多い）
3. 以下を記入する：

| 項目 | 書くこと |
|------|----------|
| タイトル | 何をしたか（1行） |
| 説明 | なぜしたか・レビュー時に伝えたいこと |

4. 「Create pull request」をクリック

**レビュワーがすること：**

- 変更内容（差分）を見る
- コメントで質問・指摘する
- 問題なければ「Approve（承認）」する

**確認問題：** プルリクエストの「Files changed」タブを開くと、何が表示されますか？

## ステップ 6：マージする

### git merge とは

`git merge` は、**あるブランチの変更を別のブランチに取り込むコマンド**です。

```
# マージ前
main:    A - B - C
                  \
feature:           D - E

# マージ後（mainにfeatureを取り込んだ）
main:    A - B - C - D - E
```

「featureブランチで積み重ねたコミット（D・E）を、mainの歴史に合流させる」イメージです。

### 基本の流れ

レビューでApproveが出たら、mainに取り込みます。

```bash
# ① 取り込まれる側（main）に移動する
git checkout main

# ② 自分のブランチをmainに取り込む
git merge feature/自分の名前-練習
```

> **ポイント：** 「どこにいるか」がマージの向きを決めます。
> `git checkout main` してから `git merge feature/〇〇` ＝「mainにfeatureを取り込む」

またはGitHub UI上で「Merge pull request」ボタンを押してもOKです（チームの運用に従う）。

### マージ後の確認

```bash
# mainの履歴に自分のコミットが入ったか確認する
git log --oneline
```

## ステップ 7：コンフリクトを体験・解決する

コンフリクトとは「同じファイルの同じ箇所を2人が別々に変えた」ときに起きます。
エラーではなく、**Gitが「どちらを採用するか判断してほしい」と知らせているサイン**です。

### コンフリクトを意図的に発生させる

1人でコンフリクトを再現する手順です。

```bash
# ① mainで練習用ファイルを作り、コミットする
git checkout main
echo "最初の内容" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "練習ファイルを追加"

# ② mainから新しいブランチを切る
git checkout -b feature/conflict-practice

# ③ ブランチ上でファイルを編集してコミットする
echo "ブランチで書いた内容" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "ブランチ側の変更"

# ④ mainに戻り、同じファイルの同じ行を別の内容で編集してコミットする
git checkout main
echo "mainで書いた内容" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "main側の変更"

# ⑤ ブランチをmainにマージする → コンフリクト発生！
git merge feature/conflict-practice
```

**この時点でターミナルに表示されるメッセージ：**

```
Auto-merging conflict-practice.txt
CONFLICT (content): Merge conflict in conflict-practice.txt
Automatic merge failed; fix conflicts and then commit the result.
```

どのファイルでコンフリクトが起きているか確認する：

```bash
git status
```

`both modified:` と表示されているファイルがコンフリクト中のファイルです。

---

### コンフリクトが起きたときのファイルの中身

```
<<<<<<< HEAD（mainの内容）
mainで書いた内容
=======
ブランチで書いた内容
>>>>>>> feature/conflict-practice
```

| 記号 | 意味 |
|------|------|
| `<<<<<<< HEAD` | ここから下が「今いるブランチ（main）の内容」 |
| `=======` | 区切り線 |
| `>>>>>>>` | ここから上が「マージしようとしたブランチの内容」 |

---

### 解決手順

1. コンフリクト中のファイルをエディタで開く
2. `<<<<<<<`・`=======`・`>>>>>>>` の記号を探す
3. 残したい内容だけを残し、**記号ごと削除する**
4. 保存してコミットする

**解決後のファイル例（両方を残す場合）：**

```
mainで書いた内容
ブランチで書いた内容
```

```bash
git add conflict-practice.txt
git commit -m "コンフリクトを解決"
```

**確認問題：** コンフリクトは「誰かのミス」ですか？

> → いいえ。複数人が同時に作業していれば自然に発生します。
> 正しく解決できれば何の問題もありません。
